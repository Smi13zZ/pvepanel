# 这个面板能实现什么功能

- 日期：2026-11-05
- 问题：「在飞牛上做原生 fpk 版 PVE 监控面板，到底能实现哪些功能」
- 依据：官方 API schema 全量反序列化（680 method / 437 叶子端点）+ PVE 源码核对 + 真机实测，不是拍脑袋列的
- 结论：**只用「只读」权限（PVEAuditor），就足以做出一个信息密度远超原报告规划的监控面板**；真正做不了的只有 CPU 温度、风扇转速、单网卡吞吐这三类

---

## 一、一句话答案

**它能把 PVE 的「集群 → 节点 → 虚拟机 → 存储 → 磁盘 → 网络 → 任务」整条链路做成一个只读的、手机也能看的仪表盘，并且额外送三件原报告没提、但运维最想要的东西：备份覆盖缺口、HA/复制状态、证书与订阅到期。**

拿不到的是：CPU/主板温度、风扇转速、单网卡实时吞吐（这三项 PVE API 层根本没有，见第五节）。

---

## 二、权限分层：先看你能拿到哪一档

这决定了功能边界，所以放在最前面。

| 档位 | 需要的权限 | 能覆盖 |
|---|---|---|
| **A. 只读（推荐，v1）** | 单角色 `PVEAuditor`，授在 `/` 且 propagate | 本报告第二~四节的全部功能 |
| **B. 日志增强** | + `Sys.Syslog` | 节点 journal、syslog、防火墙日志 |
| **C. 配置可见** | + `Sys.Modify` | APT 待更新列表、USB 设备列表 |
| **D. 控制（v2）** | + `VM.PowerMgmt` / `Sys.PowerMgmt` | 启停、快照创建、备份触发 |

我把「只读档到底够不够」当成了一个可验证的问题，逐端点算了权限表达式（含 `or`/`any` 组合），结果：

**只读档覆盖 48 个候选端点里的 42 个。** 缺的 6 个全是「需要写权限才能看」的边角料，不是核心功能：

| 端点 | 缺的权限 | 影响 |
|---|---|---|
| `/nodes/{node}/journal`、`/syslog` | `Sys.Syslog` | 看不了系统日志（可用 `/cluster/log` 替代一部分） |
| `/nodes/{node}/firewall/log` | `Sys.Syslog` | 看不了防火墙日志 |
| `/nodes/{node}/apt/update` | `Sys.Modify` | 看不了「有哪些包要更新」（但 `apt/versions` 能看版本，见下） |
| `/nodes/{node}/apt/changelog` | `Sys.Modify` | 同上 |
| `/nodes/{node}/hardware/usb` | `Sys.Modify` | 看不了 USB 设备直通列表（PCI 设备能看） |

> 注意 `qemu/{vmid}/agent/network-get-interfaces`（读虚拟机内 IP）**只读档是够的**——它接受 `VM.GuestAgent.Audit`，而 `PVEAuditor` 里就含这一项。这是个好功能，别被「Agent」两个字吓退。

## 三、能做的功能（按页面组织）

每一条都标了数据来源，方便核对。

### 3.1 总览页 —— 一屏看清集群死活

| 功能 | 数据来源 | 说明 |
|---|---|---|
| 集群健康度（quorate / 在线节点数 / 版本） | `/cluster/status` | 集群有没有脑裂、节点掉没掉，一眼看到 |
| 节点卡片（CPU / 内存 / swap / 负载 / 运行时长） | `/nodes/{n}/status` | `loadavg` 三档、`memory.available`（PVE 8+）、`cpuinfo` 型号与核心数 |
| 内核与 PVE 版本 | 同上 + `/version` | `current-kernel.release`（PVE 8+）、`pveversion`、`boot-info.mode`（UEFI/Legacy）、`boot-info.secureboot` |
| **备份覆盖缺口** | `/cluster/backup-info/not-backed-up` | **原报告没提，但这是最有价值的一条**：直接列出「没有任何备份任务覆盖的 VM/CT」。运维最怕的就是这个 |
| 全部 VM/CT 一张表（状态/CPU/内存/磁盘/网络/标签） | `/cluster/resources` | 一次请求拿全集群，不用按节点循环；含 `hastate`、`lock`、`template`、`tags` |
| HA 状态 | `/cluster/ha/status/current` + `/cluster/ha/status/manager_status` | 哪台机器在 HA 管理下、当前跑在哪个节点、仲裁状态 |
| 告警条（自动汇总） | 上述组合 | 见 3.8 |

**首屏提速的一个技巧**：Token 还没配、或者失效的瞬间，也能显示「PVE 在线 / 版本 9.2.21 / 节点名 Chin」——因为根页面和 `/api2/json/access/domains` 都**免认证**，4~6 ms 就回。这比显示一个空白页强得多。

### 3.2 曲线页 —— 历史趋势

| 功能 | 数据来源 | 说明 |
|---|---|---|
| 节点 CPU / 负载 / iowait | `/nodes/{n}/rrddata` | 19 个数据源，含 `loadavg` `cpu` `iowait` `memused` `netin` `netout` `memavailable` |
| 节点 PSI 压力曲线（PVE 9） | `rrddata` 的 `pressure*` | 5 个压力数据源，能看到「是不是被 IO 卡住了」而不只是「CPU 高」 |
| 内存 / swap / 根分区趋势 | `rrddata` | `memtotal` `memused` `swaptotal` `swapused` `roottotal` `rootused` |
| 虚拟机 / 容器个人曲线 | `/nodes/{n}/qemu|lxc/{vmid}/rrddata` | 17 个数据源，含 `diskread` `diskwrite` `netin` `netout` `memhost` |
| 五档时间窗 | 参数 `timeframe` | hour / day / week / month / year，PVE 9 还多一个 **decade**（RRD 里确实存了约 10 年的 RRA，只是旧版没在 API 里放开） |
| 存储用量曲线 | `rrddata`（存储） | `total` `used` 两个数据源 |

**一个必须避开的坑**：节点级 RRD **没有 `diskread` / `diskwrite`**（那是 VM/CT 级才有的），也**没有 `memfree`**（PVE 9 是 `memavailable`）。按 `memfree` 写死会拿到一片空白。

### 3.3 虚拟机 / 容器页 —— 信息量最大的一块

| 功能 | 数据来源 | 说明 |
|---|---|---|
| VM 与 CT 混排列表 | `/nodes/{n}/qemu`、`/lxc` | 状态徽标、CPU/内存占用、uptime |
| 详情：CPU / 内存 / 磁盘 IO / 网络 | `.../{vmid}/status/current` | PVE 9 有 32 个字段，含 `memhost`（宿主机侧实际占用，比 `mem` 更真实） |
| **PSI 压力指标** | 同上，6 个 `pressure*` | 能回答「这台 VM 是被 CPU 饿着还是被 IO 卡着」，比单纯看占用率有用得多 |
| 配置摘要（只读） | `.../{vmid}/config` | 核数、内存、磁盘、网卡、启动顺序、`autostart`、`tags`、`description` |
| **快照列表** | `.../{vmid}/snapshot` | 有几份快照、什么时候打的、占多少空间。只读档就能看 |
| **虚拟机内 IP** | `.../{vmid}/agent/network-get-interfaces` | 装了 qemu-guest-agent 就能直接读到 VM 里的 IP，不用登进去看 |
| 运行态细节 | `.../{vmid}/status/current` | `running-qemu` / `running-machine`（qemu 版本、machine type）、`agent`（agent 是否可用）、`lock`（是否卡在某个操作上） |
| 模板标记 | `/cluster/resources` 的 `template` | 区分模板与实例，别把模板算进「运行中」 |

**这里有个降级要点**：PSI、`memhost` 是 **PVE 9 独有**（PVE 7/8 一个都没有）。代码要写成「字段存在才渲染」，不要写 `if (major >= 9)`——自编译版本、未来 9.x 新字段都会误判。

### 3.4 存储页

| 功能 | 数据来源 | 说明 |
|---|---|---|
| 各存储容量水位 | `/nodes/{n}/storage` | `total` `used` `avail` `used_fraction`、类型、`content`、`shared`、`enabled` |
| 单个存储详情 | `.../storage/{storage}/status` | 同上，单个查 |
| 存储池分组 | `/pools` | PVE 的 pool 概念，可以把 VM 按业务分组显示 |
| 存储与磁盘的对应关系 | `/nodes/{n}/disks/directory`、`disks/zfs`、`disks/lvm`、`disks/lvmthin` | 能看到「这个目录存储挂在哪个盘上」「ZFS 池健康度」「LVM 卷组剩多少」 |

**四类存储结构都能看到**：目录存储、ZFS 池、LVM 卷组、LVM thin pool——这比原报告只写「各存储 used/total/avail」细一档。

### 3.5 磁盘与硬件页

| 功能 | 数据来源 | 说明 |
|---|---|---|
| 物理盘清单 | `/nodes/{n}/disks/list` | 型号、容量、序列号、WWN、类型、`health`、`wearout`（SSD 寿命，**schema 里没声明但实际会返回**） |
| **磁盘温度** | `.../disks/smart` | ATA 盘取 `attributes[id=="194"].raw` 首 token；NVMe/SAS 从 `text` 正则抠。**每块盘一次请求，只读档就够** |
| SMART 健康详情 | 同上 | `health`、`attributes`（重映射扇区、通电时间等）、`wearout` |
| PCI 直通设备清单 | `/nodes/{n}/hardware/pci` | 显卡、网卡、HBA，看哪些设备可直通（只读档够，因为接受 `Sys.Audit`） |
| 节点硬件报告 | `/nodes/{n}/report` | PVE 自己生成的系统信息汇总，CPU 型号、内存插槽、内核参数 |
| 证书状态 | `/nodes/{n}/certificates/info` | 节点证书到期时间 |

**温度这块要说清楚**：能拿到的是**磁盘温度**。CPU 温度、主板温度、风扇转速——**任何纯 API 路径都拿不到**（下面第五节详述）。

### 3.6 网络页

| 功能 | 数据来源 | 说明 |
|---|---|---|
| 网卡 / 桥 / VLAN / bond 配置 | `/nodes/{n}/network` | 接口名、类型、IP/CIDR、网关、桥接端口、VLAN 感知、bond 成员 |
| 单个接口详情 | `.../network/{iface}` | 同上，单个查 |
| 虚拟机网卡实时计数 | `/nodes/{n}/netstat` | **注意：只有 tap/veth（即 VM/CT 的虚拟网卡），没有物理网卡吞吐** |
| 防火墙规则（只读） | `/nodes/{n}/firewall/rules`、`/cluster/firewall/rules` | 规则列表、启用状态 |

**必须说清的限制**：`/network` **只有配置，没有任何流量统计**；整个 API 里也**没有「单物理网卡吞吐」端点**。想要物理网卡实时速率，只能：
- 用 `rrddata` 的节点级 `netin`/`netout`（全节点合计，分不出是哪块网卡）；
- 或者 v2 走 SSH 读 `/proc/net/dev`（破坏零侵入定位）。

原报告写「网卡/桥/vlan 配置与统计」，**「统计」这两个字是错的**。

### 3.7 任务与运维页

| 功能 | 数据来源 | 说明 |
|---|---|---|
| 集群级任务历史 | `/cluster/tasks` | 全集群的任务，含类型、发起人、状态、起止时间 |
| 节点级任务历史 | `/nodes/{n}/tasks` | 支持按 `vmid` / `typefilter` / `statusfilter` / `userfilter` / 时间范围过滤 |
| 备份任务配置 | `/cluster/backup` | 有哪些备份任务、调度、保留策略、包含哪些 VM |
| 备份覆盖缺口 | `/cluster/backup-info/not-backed-up` | 见 3.1，这个值得单独做一张卡 |
| 复制状态 | `/cluster/replication`、`/nodes/{n}/replication` | 跨节点复制作业的健康度与延迟 |
| 系统服务状态 | `/nodes/{n}/services` | pveproxy / pvedaemon / pvestatd 等是否 active，含 `active-state` `unit-state` |
| 集群日志 | `/cluster/log` | 只读档能看，但 `Sys.Syslog` 才能看全部 |
| 订阅状态 | `/nodes/{n}/subscription` | `status` `level` `nextduedate`——**到期前提醒是刚需** |
| 服务器时间与时区 | `/nodes/{n}/time` | 时间漂移会影响集群，顺手看一眼 |
| 关键包版本 | `/nodes/{n}/apt/versions` | pve-manager 等关键包版本（**注意：想看「有哪些包待更新」需要 `Sys.Modify`，只读档看不到**） |
| DNS / hosts 配置 | `/nodes/{n}/dns`、`/hosts` | 只读展示 |

### 3.8 告警（这是原报告漏掉的一整块）

原报告的 v1 里只有一句「告警条（节点离线、存储超阈值、订阅到期）」，其实这块可以做得实在得多——**因为 fpk 后端是常驻进程，可以主动巡检并推送**，不需要用户开着页面。

可实现的告警类型：

| 告警 | 判据 | 数据来源 |
|---|---|---|
| 节点离线 / 集群失联 | `type=="node"` 且 `status!="online"`，或 `quorate==0` | `/cluster/status` |
| 存储水位超阈值 | `used_fraction > 阈值`（可按存储单独设） | `/nodes/{n}/storage` |
| 节点内存/CPU 持续高 | `rrddata` 最近 N 点均值 | `rrddata` |
| **VM 无备份覆盖** | 出现在 `not-backed-up` 列表里 | `/cluster/backup-info/not-backed-up` |
| 备份任务失败 | 任务 `status != "OK"` 且 `type=="vzdump"` | `/cluster/tasks` |
| 磁盘 SMART 异常 | `health != "PASSED"` 或 `wearout` 低于阈值 | `disks/list`、`disks/smart` |
| **磁盘温度超阈值** | ATA `194` / NVMe `text` 解析值 | `disks/smart` |
| 订阅即将到期 | `nextduedate` 距今 < N 天 | `/subscription` |
| 节点证书即将到期 | `certificates/info` 的 `notafter` | `certificates/info` |
| **Token 即将过期 / 已失效** | 首个 401 + Token `expire` 时间 | 自身状态 |
| PVE 节点有告警级内核消息 | `/cluster/log` 过滤 | `/cluster/log`（需 `Sys.Syslog` 才全） |

推送通道可以直接复用已有 fpk 应用那套（Bark / Server 酱 / PushPlus / WxPusher / Telegram / 企业微信 / 钉钉 / Slack / Webhook）——后端是 Python 常驻进程，做这件事的成本很低。

**这条对「飞牛上做面板」特别有意义**：飞牛本身是 7×24 常开的，放一个轻量巡检进程很自然；而 PVE 那边如果不装额外东西，是没有「推送到手机」能力的。

### 3.9 设置页

| 功能 | 说明 |
|---|---|
| PVE 地址 + Token | Token 存 `@appdata/token.json` + `chmod 600`，前端永不回显（用 `__SET__` 掩码） |
| 连接状态诊断 | 分开展示「能连通吗」「证书什么情况」「Token 有效吗」「权限够吗」——401 和 403 必须分开提示 |
| 刷新间隔 / 告警阈值 | 按页面、按指标分别设 |
| 导入 CA 证书 / 指纹 pinning | 应对 PVE 自签证书 |
| 日志查看 | 面板自己的运行日志 |
| 版本检查 | 面板自身的更新提示 |

## 四、原报告没列出来、但值得做的

这几条我在核对 API 时发现能拿到，原报告的 v1 规划里没有：

| # | 功能 | 为什么值得做 |
|---|---|---|
| 1 | **备份覆盖缺口**（`not-backed-up`） | 一个端点就能回答「哪些机器没有备份」。这是运维最容易出事的地方，成本极低 |
| 2 | **HA 状态** | 有 HA 的集群，看「当前主节点是谁、仲裁是否正常」是刚需 |
| 3 | **复制状态** | 跨节点复制作业的延迟与健康度 |
| 4 | **虚拟机内 IP**（guest agent） | 装过 agent 的 VM 直接显示 IP，不用一台台登进去看。只读档就够 |
| 5 | **快照列表** | 有几份快照、多老、占多少空间。快照堆积是常见事故 |
| 6 | **SSD 寿命 wearout** | schema 里没声明但实际会返回，白拿的信息 |
| 7 | **证书与订阅到期** | 到期前提醒，避免半夜失联 |
| 8 | **PSI 压力曲线** | 目标机是 PVE 9，六字段齐全，但原报告只把它当成 VM 列表的一个字段，其实做成曲线更能定位问题 |
| 9 | **PCI 直通设备清单** | 有直通需求的用户很需要 |
| 10 | **免认证首屏** | Token 没配也能显示「PVE 在线 / 版本 / 节点名」，不是空白页 |
| 11 | **主动告警推送** | 见 3.8，飞牛常开的特性正好用上 |
| 12 | **decade 时间窗** | PVE 9 才有，RRD 里存了约 10 年数据 |

## 五、做不了的（硬边界，别绕）

| 做不到 | 原因 | 绕过方案 | 评价 |
|---|---|---|---|
| **CPU 温度 / 主板温度** | 全 API `temperature` / `sensor` / `thermal` 关键词命中 **0** | SSH 到 PVE 跑 `sensors -j` | 破坏「纯 API、零侵入」定位，v2 再议 |
| **风扇转速** | `fan` / `rpm` 命中 **0** | 同上 | 同上 |
| **单物理网卡吞吐** | `/network` 只有配置；`netstat` 只覆盖 tap/veth | `rrddata` 的节点级 `netin/netout`（合计）；或 SSH 读 `/proc/net/dev` | v1 用合计值够用 |
| **节点级磁盘 IO 曲线** | 节点 RRD 没有 `diskread`/`diskwrite`（那是 VM 级） | 用 `iowait` 间接反映；或把各 VM 的 `diskread` 求和 | v1 用 iowait |
| **系统 journal / syslog 全文** | 需要 `Sys.Syslog` | 提权，或用 `/cluster/log` 替代 | v1 用 `/cluster/log` |
| **APT 待更新列表** | 需要 `Sys.Modify` | 提权 | v1 只显示关键包版本 |
| **启停 / 快照 / 备份触发** | 需要 `VM.PowerMgmt` 等写权限 | v2 单独评估 | 原报告也归到 v2 |

**一个特别容易误判的坑**：模糊搜 `Temp` 会命中 20 处，但**全部**落在 `notes-template` / `Template`（备份备注模板）里，跟温度毫无关系。信这个就会以为「PVE 有温度字段」。

## 六、建议的 v1 页面清单

按「信息价值 / 实现成本」排的优先级：

| 优先级 | 页面 | 核心内容 | 估时 |
|---|---|---|---|
| P0 | **总览** | 集群健康 + 节点卡片 + 备份缺口 + 告警条 | 0.5 天 |
| P0 | **虚拟机/容器** | 混排列表 + 详情（PSI/磁盘IO/网络/快照/IP） | 1 天 |
| P0 | **设置** | 地址/Token/诊断/阈值 | 0.5 天 |
| P1 | **曲线** | 节点五档 + VM 个人曲线 | 0.5 天 |
| P1 | **存储** | 水位 + 磁盘结构（ZFS/LVM/目录） | 0.5 天 |
| P2 | **磁盘** | 物理盘 + SMART + 温度 | 0.4 天 |
| P2 | **任务** | 任务历史 + 复制 + HA + 订阅 | 0.4 天 |
| P2 | **网络** | 配置展示 + VM 网卡计数 | 0.2 天 |
| — | 告警推送 | 巡检线程 + 九种通道 | 0.5 天 |
| **合计** | | | **约 4.5 天** |

加上骨架（2.5 小时）与打包交付（1 天），**总估时 5~6 天**，与原报告一致——但功能面比原报告规划的宽（多了备份缺口、HA、复制、快照、VM IP、证书订阅到期、主动推送）。

## 七、一句话总结

**这个面板的本质价值不是「把 PVE 的 Web UI 缩小搬到飞牛上」，而是「把 PVE 里散落在七八个页面、需要点进去才能看到的状态，压缩成一屏能扫完的只读面板，并且在出问题时主动推到你手机上」。**

在只读权限下它能做到的事情，已经覆盖了日常巡检 90% 的场景。剩下的 10%（温度、启停、日志）要么是 API 层没有，要么值得单独评估权限扩展。
