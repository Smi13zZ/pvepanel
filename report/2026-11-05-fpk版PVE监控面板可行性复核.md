## 一、结论先行

### 1.1 判定

**技术上完全可行，没有硬阻塞。五条关键链路全部在真机上跑过：**

| 链路 | 状态 | 证据 |
|---|---|---|
| 飞牛运行时能否承载纯标准库后端 | ✅ | Debian 12 / Python 3.11.2 / fnpack 1.2.4，空壳服务 RSS 19 MB、CPU 0.1%（fnos-test 实测） |
| fpk 骨架能否直接复用到这个场景 | ✅ | 在 fnos-test 造骨架 → 打包 66 KB → 安装 8 s → 服务起来 → CGI 转发 → 卸载 → 重装，**全链路走通** |
| 飞牛 → PVE 8006 出站是否畅通 | ✅ | TLS 握手 23 ms，TLSv1.3，无防火墙阻碍 |
| PVE API 能否覆盖监控面板需要的数据 | ✅（除 CPU/主板温度、风扇） | 437 个叶子端点逐个核对官方 schema |
| Token 能否安全落盘 | ✅（有边界，见 4.5） | `@appdata` 770 root:root + chmod 600，普通用户实测 Permission denied |

### 1.2 但参考报告有两处必须修正

**第一处（会带偏架构）：那 3 秒不是 API 往返延迟。**

参考报告 §2.4 把「未认证请求固定 3.006~3.007 s」当作「单次 API 往返 ~3 s」，进而在 §7 风险 1 推出「10 个端点 = 30 秒，必须并发 + 缓存」。

实测与源码都证明：**那 3 秒只挂在 HTTP 401 分支**，是 PVE 硬编码的「未授权固定延时」，而且语义是「补足到 3 秒」而不是「额外加 3 秒」。

```
同一 daemon、同一条 /api2/json 管线：
  /api2/json/access/domains  200   ttfb 4.0 ms   ← 免认证
  /                            200   ttfb 5.6 ms   ← 静态页
  /api2/json/version          401   ttfb 3006 ms  ← 需认证，未认证
  /api2/json/nonexistent      401   ttfb 3006 ms  ← 路径不存在也一样
```

源码出处 `pve-http-server/src/PVE/APIServer/AnyEvent.pm`：

```perl
# L1038-1043：正常鉴权流程结束后，401 时补延时
my $delay = 0;
if ($res->{status} == HTTP_UNAUTHORIZED) {
    # always delay unauthorized calls by 3 seconds
    $delay = 3 - tv_interval($reqstate->{starttime});
    $delay = 0 if $delay < 0;
}
# L1644：auth_handler 抛异常（Token 无效）时
my $delay = 3;
# L388-398：不是 sleep，是挂 AnyEvent 定时器，到点才 push_write
```

**推论**：认证成功后不存在这个延迟。实测「网络 + daemon 调度」地板是 **p50 4.4 ms**，keep-alive 复用后 **0.35~0.45 ms/请求**，300 并发零错误。所以「必须并发否则 30 秒」**不成立**。

**但这个发现把风险换了个位置，并没有消除风险**：

- 3 秒可以被并发完整吃掉——8/16/40/100/150/200 路并发 401，每路仍 ~3.01 s，墙钟只 ~3.0~3.3 s（每请求一个独立定时器，不阻塞事件循环）；
- 真正会「面板假死」的是**Token 失效**：此时每个请求 3 s 且响应头带 `Connection: close` 强制断连。8 端点串行 **24 s**，N=3 节点（2+6N 个请求）就是 **60 s**。

→ **「并发 + 缓存」的结论保留，但必须补一条硬性要求：首个 401 立刻熔断、取消其余在飞请求、停止轮询。这是必须项，不是优化项。**

顺带一个正面收获：这个特性可以反向利用——**面板首屏稳定卡在 3.0 s 附近，几乎可以断定是 Token 没过（401），而不是网络或 PVE 性能问题**。可以直接做成可读的错误提示。

**第二处：温度拿不到，但结论原因写错了。**

参考报告说「全 API 中 sensor/temperature 命中数为 0」——**属实，我复核确认**（`fan`/`rpm` 也是 0）。但这只说明没有叫这个名字的字段，不能推出「PVE 拿不到温度」。磁盘温度确实能拿，只是藏得深（见 3.3）。

### 1.3 一句话评价原报告

**方向判断、路线选择（A 自研轻量面板）、v1 只读范围、安全定位（后端代理挡 Token）全部正确，可以直接作为立项依据。** 需要改的是三件事：延迟论据、温度取法、以及它漏掉的一批 fpk 侧硬约束（自启无守护、service_port 语义、直连端口无鉴权）。

### 3.2 需要精确化（不影响判断，影响实现）

| # | 报告原文 | 精确结论 |
|---|---|---|
| 8 | §3「磁盘 SMART（磁盘温度在此）」 | 对，但太粗。ATA 盘取 `attributes[id=="194"].raw` 的首个 token（部分盘是 `id 190`）；NVMe/SAS 只能从 `text` 自由文本正则 `(?:Temperature|Drive Temperature)\s*:\s*(\d+)\s*C`。`disks/list` **完全没有温度**，只有 health 字符串 |
| 9 | §7 风险 4「只读 PVEAuditor + Token 权限分离」 | 方向对但**漏了最关键的**：必须授在 `/` 且 propagate。`/cluster/status` 查的是 `/` 的 `Sys.Audit`，`/nodes/{node}/disks/smart` **写死根路径**——只授子树会 **403**。另外 Token 默认 `privsep=1`，有效权限 = 用户权限 ∩ token 自己的 ACL，**ACL 要额外授给 token 本身**；`expire` 不填 = **永不过期** |

| 12 | §2.2「根路径 200」 | 不止 200：根页面**免认证**就泄露 PVE 版本（`9.2.21`）、节点名、架构、widget-toolkit 版本；`/api2/json/access/domains` 也免认证 200。**Token 没配就能显示「版本 + 节点名 + 可达性」** |

### 3.3 报告完全没覆盖、但会咬人的

1. **探活别打需要认证的端点**。拿 `/api2/json/version` 探活每次白烧 3 秒；应打 `GET /`（5 ms）或 `/api2/json/access/domains`（4 ms，还免费返回认证域列表）。
2. **PVE 不支持 HTTP/2**（无 ALPN），只有 HTTP/1.1；2xx 保活、4xx 强制 `Connection: close`。一次 TLS 握手 2.3~3.2 ms，比一次 API 处理还贵 → 后端**必须维护长连接**（4~6 条足够，服务端默认 3 worker / 500~800 连接上限）。
3. **PVE 默认不做频率封禁**。累计 1000+ 次 401，无 429、无延时递增、无封 IP。所以不用担心轮询打爆，但也不该滥用。
4. **manifest 漏了三个必需项**：`ctl_stop = true`（否则卸载留残进程）、`checkport = false`（否则用户换端口就装不上）、以及 `config/resource` 这个**文件必须存在**，缺了 fnpack 直接 `Packing failed`。
5. **`index.cgi` 的三级端口兜底不能简化**。实测 `trim_http_cgi` 二进制里 `TRIM_PKGVAR` 出现 **0 次**——CGI 环境里根本没有这个变量，只写第一级兜底会永远落到默认端口，改端口后桌面入口就废了。
6. **401 与 403 必须分开处理**。401 = Token 无效/过期/用户被禁（配置问题，且被加 3 秒）；403 = 权限不足或授权路径错（`raise_perm_exc` 固定 `HTTP_FORBIDDEN`，**不加延时**）。混为一谈会让用户完全无从下手。

## 四、可行性重估

### 4.1 运行时与骨架：成本比报告估的还低

报告估「骨架 0.5 天」。实测结果是 **≈ 2.5 小时（含一次真机回归）**，因为 9 个生命周期脚本里 8 个能原样复用，`index.cgi` 原样复用，只有 `cmd/main` 要改 7 处（进程名、日志名、默认端口、env 前缀）。

骨架源码已经在 `tmp/fpk-skeleton/src/` 备好，含九档图标，**实测能打包、能安装、能起服务**。立项后移到 `src/` 即可。

资源占用不是问题：空壳 RSS 19 MB / VSZ 100 MB / CPU 0.1%；包体积 66 KB（加 Vue 运行时估计 300 KB–1 MB）；**没有 cgroup 限制**，也没生成 systemd unit。

### 4.2 API 能力：比报告写的更全，但温度仍是硬边界

**能拿到**：集群资源、节点状态（含 `current-kernel` / `boot-info` / `memory.available`）、节点与 VM/CT 的 RRD 曲线、VM/CT 状态（PVE 9 共 32/24 字段，含 6 个 PSI 压力指标）、存储容量、物理磁盘列表、SMART 摘要与**磁盘温度**、任务历史、系统服务、订阅状态、版本。

**拿不到（硬边界，与报告判断一致）**：

- CPU 温度、主板温度 —— 全 API `temperature` / `sensor` / `thermal` 命中 **0**；
- 风扇转速 —— `fan` / `rpm` 命中 **0**；
- 单网卡吞吐 —— `/network` 只有配置，`netstat` 只覆盖 tap/veth。

> 一个容易踩的假阳性：模糊搜 `Temp` 会命中 20 处，但**全部**落在 `notes-template` / `Template`（备份备注模板）里，与温度无关。信这个就会误判成「有温度字段」。

**目标机是 PVE 9.2.21**，报告风险 2 假设的「PSI 仅新版有」在目标机上不成立（六字段齐全），风险下调。但代码仍应按「字段存在才渲染」写——不要用版本号判断，也不要拿 `returns` schema 当字段白名单（`wearout`、`memhost` 都是真实返回但未在 schema 声明的字段，按 schema 裁剪会丢数据）。

### 4.3 安全：报告的安全模型是对的，但补一个必须做的动作

报告的核心安全设计——**浏览器永远不接触 PVE 地址和 Token，所有请求由本机服务转发**——完全成立，且是这套架构最有价值的部分。

但实测发现一个报告没提的缺口：**CGI 那条路有 fnOS 登录闸门，直连面板端口没有**。这是 fpk 应用的通用行为（qbpanel 的 8898、fn-emule 的 17581 一样），不是这个项目引入的，但对这个项目影响更大——因为面板背后是整台 PVE 的只读视图。

**必须做的动作**：面板默认 `listen 127.0.0.1`，只让 CGI 这条路进来，天然继承 fnOS 登录鉴权。只有在用户明确要求「局域网直连」时才放开，且**必须自带面板密码**。

Token 存储：`@appdata/token.json` + `chmod 600`（先写 `.tmp` 再 `os.replace`）。前端永不回显，用 `__SET__` 掩码。

> 这里有一个 qbpanel 生产机实际炸过的坑，必须提前防御：**设置页保存时如果把含掩码的整份 draft 提交上去，`__SET__` 会被当成新 Token 存盘**，且无法自动恢复。要两道防线——服务端收到 `__SET__` 或空串就沿用旧值；前端只提交真正改动的分区。

### 4.4 权限：一条命令的差别，决定磁盘页能不能用

`PVEAuditor` 单角色就够（它由 `privgroups` 的 audit 项自动拼成，已含 `Sys.Audit` + `Datastore.Audit` + `VM.Audit` + `Pool.Audit` + `SDN.Audit` + `Mapping.Audit`，不用再拼），**但必须授在 `/` 且 propagate**。

```bash
pveum user add monitor@pve --comment "fnOS PVE panel (read-only)"
pveum acl modify / --users monitor@pve --roles PVEAuditor --propagate 1

# Token 默认 privsep=1（权限取交集），ACL 必须额外授给 token 本身
pveum user token add monitor@pve dash --privsep 1 --expire <unix 秒> --comment "fnOS panel token"
pveum acl modify / --tokens 'monitor@pve!dash' --roles PVEAuditor --propagate 1
```

只授在 `/nodes/x` 子树的后果：`/cluster/status` 与 `/nodes/{node}/disks/smart` 直接 **403**。这是最容易踩的坑——看着「够用」，装上才发现磁盘页和集群状态页是空的。

### 4.5 自启与守护：一个必须写进 README 的限制

**开机自启是有的**：appcenter 启动时批量拉起所有 `status=running` 的应用，实测重启 appcenter 后应用被拉回，journal 里有 `APP_AUTO_STARTED` 事件。

**但没有崩溃监护**：`kill -9` 之后 120 秒轮询端口全程不通，DB 状态从 `running` 掉到 `start`，没有任何东西拉起它。qbpanel 和 fn-emule 有同样的特性，是既有惯例不是新风险。

两个选择：README 写清「异常退出后到应用中心点启动」，或者在 python 里起一个自监管线程。前者够用，后者更稳。

## 五、修正后的方案建议

### 5.1 路线选择：维持路线 A

三条路线的对比结论不变，A（自研轻量面板）依然是唯一合理选择。补两条实测支撑：

- **B（打包 Grafana）**：fpk 不适合容器编排，且镜像 500 MB+ 与「66 KB 骨架 + 300 KB 面板」差三个数量级；
- **C（iframe 嵌 PVE 原生 UI）**：除了报告说的跨站登录态问题，还有一条——PVE 根页面本身要认证，而 `PVEAuthCookie` 是 `SameSite` 受限的，嵌不进去。

### 5.2 架构要点（相对报告的变化）

报告讲对的部分保留：后端代理挡 Token、并发抓取、分层缓存、TTL 按数据变化速度定。

需要新增或修改的：

| 项 | 修正后做法 | 理由 |
|---|---|---|
| 并发 | 保留，但**并发度压到 4~6 条长连接** | 长连接比并发度更值钱（0.45 ms vs 2.7 ms/请求）；服务端默认 3 worker，堆连接没收益 |
| 缓存 | 保留，但**理由从「躲 3 秒」改为「降低后端计算成本 + 故障态止血」** | rrddata / SMART 的后端耗时才是真成本 |
| 熔断 | **新增**：首个 401 → 取消在飞请求 + 停止轮询 + 显式告警 | Token 失效时 8 端点串行 24 s、N=3 节点 60 s，这才是「面板假死」的真相 |
| 探活 | **新增**：用 `GET /` 或 `/api2/json/access/domains` 探活，永不拿需认证端点探活 | 每次白烧 3 秒 |
| 首屏 | **增强**：Token 未配置时也能显示「PVE 在线 / 版本 / 节点名」 | 根页面免认证就泄露这些信息，白送的 |
| 监听地址 | **改**：默认 `127.0.0.1`，只走 CGI | 直连端口没有 fnOS 登录鉴权 |
| 错误分流 | **新增**：401 与 403 文案分开 | 401 = Token 问题，403 = 授权路径问题，混在一起用户无从下手 |
| 字段降级 | **改**：一律「字段存在才渲染」，不用版本号判断、不用 schema 当白名单 | `wearout` / `memhost` 是真实返回但未声明 |

### 5.3 建议的刷新节奏（可直接写进设计）

| 数据 | 端点 | TTL | 理由 |
|---|---|---|---|
| 可达性 + 版本 + 节点名 | `GET /`（免认证） | 5 s | 4~6 ms 白送；Token 失效时仍能显示「PVE 在线」 |
| 集群总览 | `/cluster/resources` | 5~10 s | 一次拿全量，避免 N×M 放大 |
| 节点状态 / VM·CT 列表 | `/nodes/{n}/status`、`/qemu`、`/lxc` | 5~10 s | pvestatd 本身 10 s 周期，更快没意义 |
| 存储容量 | `/nodes/{n}/storage` | 30 s | 变化慢 |
| 曲线 | `rrddata` | 60~300 s，**仅曲线页可见时拉** | 后端计算重，RRD 粒度 1 min |
| 磁盘 / SMART | `/disks/list`、`/disks/smart` | 300 s，**每盘一次请求** | smartctl 最慢的一类，绝不能进首屏 |
| 任务 / 订阅 | `/tasks`、`/subscription` | 60 s | 变化慢 |

### 5.4 温度策略（相对报告的调整）

报告推荐「v1 只用磁盘 SMART 温度」——**采纳**，但实现比报告写的复杂：

```python
def extract_disk_temp(smart):
    if smart.get("type") == "ata":
        for a in smart.get("attributes") or []:
            if a.get("id") in ("194", "190") or "Temperature" in (a.get("name") or ""):
                m = re.match(r"\s*(\d+)", a.get("raw") or "")
                if m: return int(m.group(1))
    m = re.search(r"(?:Temperature|Drive Temperature)\s*:\s*(\d+)\s*C", smart.get("text") or "")
    return int(m.group(1)) if m else None
```

**CPU / 主板温度、风扇转速 v1 直接不做**。不是妥协，是 API 层根本没有——SSH `sensors` 或装 exporter 都会破坏「纯 API、零侵入」的定位，留给 v2 重新评估。

## 七、修正后的风险表

| # | 风险 | 影响 | 规避 |
|---|---|---|---|
| 1 | **Token 失效时面板假死**（每请求 3 s + 强制断连，N=3 节点 60 s） | 高 | **首个 401 立刻熔断**，取消在飞请求、停止轮询、给出「Token 无效/过期」的明确文案。这是必须项 |
| 2 | **直连面板端口无 fnOS 登录鉴权** | 高 | 默认 `listen 127.0.0.1`；放开到 `0.0.0.0` 时必须自带面板密码 |
| 3 | **授权路径错导致 403**（`PVEAuditor` 授在子树） | 中 | README 给可直接抄的 `pveum` 命令；面板把 403 文案写成「权限不足，请确认授在 `/` 且 propagate」 |
| 4 | **Token 掩码被当成新值存盘**（qbpanel 生产机炸过） | 中 | 两道防线：服务端遇 `__SET__`/空串沿用旧值；前端只提交改动分区 |
| 5 | PVE 自签证书（CA 不在 chain 里，`openssl verify` 返回 21） | 低 | `CERT_NONE` 是唯一零配置可行路径；设置页另提供粘贴 PEM 做指纹 pinning |
| 6 | PVE 版本字段差异（PSI/memhost 仅 9 有，`current-kernel` 仅 8+） | 低 | 一律「字段存在才渲染」，不用版本号判断 |
| 7 | 崩溃后不自愈 | 低 | README 写明；可选加自监管线程 |
| 8 | 磁盘温度解析按盘型分支 | 低 | ATA 走 `attributes[194]`，NVMe/SAS 走 `text` 正则；解析不到就隐藏，不显示 0 |
| 9 | 飞牛系统 Python 升级 | 低频 | 只用最稳定的标准库子集，不依赖第三方包（这条报告判断正确） |

## 八、待用户决策

**三个可以直接拍板的：**

1. **v1 范围**：只读监控（推荐，5~6 天）vs 含启停控制（+2 天，权限面从 `PVEAuditor` 扩到 `VM.PowerMgmt`/`Sys.PowerMgmt`）
2. **温度策略**：v1 只做磁盘温度（推荐）vs 额外加 SSH 通道取 `sensors`（破坏零侵入定位）
3. **是否先做最小原型**：用 1 天做「总览页 + 真实数据」的可运行 fpk。**现在这个选项比报告写的时候更有价值**——骨架已实测可用，原型成本降到接近「只写业务代码」。

**一件必须用户提供才能继续的：**

4. **一个只读 PVE API Token**。格式 `PVEAPIToken=<user>@<realm>!<tokenid>=<uuid>`，权限 `PVEAuditor`（授在 `/` 且 propagate）。没有它，所有「认证后很快」的结论都停留在推断层面，而且 `/disks/smart` 这类后端计算型端点的真实成本完全未知。

**一个需要确认的前提：**

5. **面板默认监听 `127.0.0.1`（只走飞牛桌面入口）是否可以接受？** 如果能接受，安全模型最干净；如果需要局域网其他设备直连，就得额外做一个面板自己的登录。
