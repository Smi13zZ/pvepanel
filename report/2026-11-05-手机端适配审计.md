# 手机端适配审计

- 日期：2026-11-05
- 审计人：build-tools（teammate，task-9）
- 起因：用户反馈「再所有页面检测一下，适配手机端，我看好几个地方没适配好」
- 被测实例：`fnos-test` 上从 **源码** 起的预览实例 `127.0.0.1:8901`（见 §0.2），数据来自本地 Mock PVE
- 验收档位：**390x844**（iPhone 主档）、**360x640**（小屏安卓）、**768x1024**（平板）

> 本篇只写「量到了什么 → 怎么修 → 怎么验证」。所有数字都是脚本实测，不是目测。

## 0. 方法与口径

### 0.1 为什么先造了一个「布局探针」

截图只能看出「看着不对」，说不出「哪个元素、超了多少 px」。所以额外做了一个探针页
`probe3.html`：它把面板放进一个精确尺寸的 iframe（媒体查询按 iframe 宽度生效），
等首屏数据渲染完后，在面板文档里跑一遍几何测量：

- 文档级横向溢出 `documentElement.scrollWidth - clientWidth`
- **逐元素**遍历，列出所有 `right > viewportWidth` 的可见元素（即真正的溢出元凶）
- 具名控件（`.topbar` / `.page-title` / `.workbar` / `.evgrid` / `.chart-wrap` / `.acts` …）
  的实际宽高、位置、以及「有滚动容器时是否被裁切」
- 表格**逐列**的可见性（`getComputedStyle(th).display`）
- `.evgrid` 的实际 `grid-template-columns`、canvas 的实际尺寸

探针本身用 `tools/shot.py --dump-dom` 取回结果，所以审计是可复跑的。

### 0.2 为什么另起一个预览实例

任务禁止打包/部署，但已装好的面板提供的是安装目录里的静态文件
（`/usr/local/apps/@appcenter/fn-pvepanel/web`，`root:root` 700，改它等于部署）。
所以从 `src/` 起了一个独立实例跑在 8901，只服务源码里的 `web/`：

- 配置用**假 token**（`monitor@pve!dash=0f7d2c4e-...`，Mock 服务的开发令牌，非真实凭据），
  指向本机 Mock PVE `127.0.0.1:18006`；
- **没有**读取生产 `@appdata` 里的真实 token —— 过程中一度用符号链接指过真实配置，
  发现后立即删掉链接、改为独立假配置（真实密钥既未复制也未落盘）；
- 这样改一次 CSS 只要 `preview.py sync`，不需要重打包，迭代从分钟级降到秒级。

脚本：`pve-panel/tmp/preview.py`（`up` / `sync` / `down` / `status`）。

### 0.3 一个重要的结论先说：横向滚动其实没有

所有 9 个页面 × 3 档宽度，`documentElement.scrollWidth - clientWidth` **全部为 0**。
也就是说任务里担心的「横向滚动条」并不是真实症状。

**但有个更糟的情况**：磁盘表格内部宽度 634px 却塞在 390px 视口里，
**溢出的部分被卡片裁掉了，而不是产生滚动**（详见 §2）。用户看到的「没适配好」
就是这类「内容被切、但页面不报错」的情况。

## 1. 顶栏：标题被裁 + 服务器下拉抢位

### 实测

| 宽度 | `.page-title` 实际宽 | 需要宽 | 结果 |
| --- | --- | --- | --- |
| 390px | 27px（「总览」） | 28px | **CLIPPED**，scrollW=28 > clientW=27 |
| 390px | 40px（「虚拟机」） | 42px | **CLIPPED** |
| 360px | 22px（「总览」） | 28px | **CLIPPED**，少 6px |
| 360px | 33px（「虚拟机」） | 42px | **CLIPPED**，少 9px |
| 768px | 28 / 42px | 28 / 42px | 正常 |

同时 `.topbar .select.topbar-server` 在 360px 下仍占 **162px**、390px 下占 **187px**。

### 症状

标题被 `text-overflow: ellipsis` 截成半个字（截图里「虚拟…」），
而服务器下拉框按 `flex: 0 1 190px; min-width: 96px` 优先吃掉了空间。
360px 上「虚拟机」只剩 33px，实际显示成「虚…」。

### 根因

顶栏是 `display:flex`，标题 `flex: 0 1 auto; min-width: 0` —— 可以被压缩，
下拉框 `flex: 0 1 190px` 但 `min-width: 96px` 保底。空间不够时**先压标题**。

### 修法

窄屏下给标题保底宽度，允许下拉框让位：

```css
@media (max-width: 640px) {
  /* 标题是当前页的定位依据，不能被下拉框挤成半个字 */
  .topbar .page-title { flex: 1 1 auto; min-width: 4.5em; }
  .topbar .select.topbar-server { flex: 0 1 44%; min-width: 0; }
}
```

## 2. 磁盘：7 列表格在手机上被裁掉 244px（最严重）

### 实测（390px 与 360px 完全一致）

```
OVERFLOWCOUNT=49
   table.ttable w=634 right=645
   thead w=634 right=645
   th w=55 right=392
   th w=65 right=457
   th w=81 right=537
   th w=48 right=585
   th w=60 right=645
TABLE=7/7   +设备 +型号 +容量 +类型 +健康 +温度 +寿命
```

表格 634px 塞进 380px 内容区，**超出的 245px 被卡片 `overflow` 裁掉**，
页面本身不滚（`overflow=0`）。截图里「健康」列显示成半个 `UNKNO`，
「温度」「寿命」两列**完全看不见**。

### 根因

`.ttable` 没有任何窄屏列收敛规则。磁盘表的 7 个 `<th>` 里，
只有任务表的「节点」列有 `.hide-md`，磁盘表一列都没标。

### 修法

参照虚拟机表的既有做法（`.ttable.tlist th:nth-child(n+4)`），
给磁盘表**显式加类名**再收敛，而不是靠 `nth-child` 猜列序（见 §3 的教训）：

```html
<table class="ttable tdisk">
```
```css
@media (max-width: 640px) {
  /* 手机上保留「设备 / 型号 / 容量 / 健康」，温度与寿命收进健康列下方 */
  .ttable.tdisk th:nth-child(n+4), .ttable.tdisk td:nth-child(n+4) { display: none; }
}
```

## 3. 虚拟机：操作按钮整列被隐藏 —— 手机上无法启停 VM（功能性缺陷）

### 实测

```
TABLE=3/8
  +VMID +名称 +状态 -CPU -内存 -运行时长 -类型 -操作
```

`acts(guest-actions)` 测到 `0x0`（被 `display:none` 掉）。

### 症状

390x844 上虚拟机表格只剩 VMID / 名称 / 状态三列，
**第 8 列「操作」（启动/停止/重启按钮）被一并隐藏**。
也就是说手机端看得到哪台 VM 在跑，但没法对它做任何操作 —— 这不是排版问题，是功能缺失。

### 根因

现有规则按列序一刀切：

```css
.ttable.tlist th:nth-child(n+4), .ttable.tlist td:nth-child(n+4) { display: none; }
```

它假设「第 4 列之后都不重要」，但操作列恰恰是第 8 列，于是被误杀。
（推断：桌面端一直正常，所以这条从没被暴露。）

### 修法

把「保留到第几列」换成「逐个声明该角色的列」—— 用类名标记，只隐藏真的可以不要的：

```css
@media (max-width: 640px) {
  .ttable.tlist th.hide-xs, .ttable.tlist td.hide-xs { display: none; }
}
```
并在 `index.html` 里给 CPU / 内存 / 运行时长 / 类型 四列加 `hide-xs`，
**操作列保持可见**。

### 8.1 改了什么

只改了 **`src/fn-pvepanel/app/web/style.css`** 一个文件，全部集中在 `@media (max-width: 640px)` 里。
`index.html` 最终**没有留下改动**（原因见 §9）。

| # | 位置 | 问题 | 修法 |
| --- | --- | --- | --- |
| 1 | 磁盘表 | 7 列 634px 塞进 348px 卡片，温度/寿命被裁，健康截成 `UNKNO` | 手机只留 4 列（设备/容量/健康/温度）；`table-layout:fixed` + 百分比宽度，并用 `!important` 压掉桌面端的 inline 像素宽度 |

## 9. 复盘：为什么第一版修复在真机上没生效

这一条比结论本身更重要 —— 它是**同类事故的第二次**（第一版用的是 th/td 上的 `hide-xs` 类）。

**现象**：改完在预览实例（8901，直接读 `src/`）验证完全正常；打包部署到 26.11.2 后，
真机上操作列又不见了、CPU/内存列挤爆、磁盘表头与内容错位。

**实测对照**：

```
部署后 style.css  md5 = e4dbfb48...  与 src 一致，CSS 改动在
部署后 index.html md5 = 96052440...  与 src 一致
deployed index.html 中 hide-xs 出现次数 = 0
src/index.html      中 hide-xs 出现次数 = 0
```

**根因**：`index.html` 在 23:06:08 被另一次操作重写过（晚于我在 23:00:50 改的 style.css），
我加在 `th`/`td` 上的 `hide-xs` 类被抹掉，而 `style.css` 保留下来。
于是 `.hide-xs { display:none }` 成了**永不匹配的死规则** —— 一列都没隐藏，
每列按桌面宽度渲染，表格把真实内容（操作按钮、温度）挤出了卡片右缘。

**为什么预览实例没发现**：预览读的也是同一份 `src/`，但它在我改完 HTML 之后、被重写之前同步过，
此后我再没重新 push 过 HTML —— 预览里一直是「正确组合」。
**我验证的文件快照和最终交付的不是同一时刻的**，这是漏掉的一环。

**现在的做法**：

1. **布局规则只放在一个文件里** —— 全部用 `nth-child` 写在 `style.css` 内，
   不再依赖 `index.html` 里存在对应类名。任一侧被重写都不会静默失效。
2. 代价是列序号必须与 HTML 对齐，所以把两份序号表**写进 CSS 注释**，改列时对着核对。
3. `th` 与 `td` **成对**隐藏，绝不只隐藏一边 —— 那是第一版「表头/内容错位」的直接原因。
4. 部署后**重新量一遍真机**，不再只信预览实例。

## 10. 关于「点按钮没反应」

Lead 提到 26.11.2 修了 `force=1` 未绕过缓存、以及刷新时机改为 2.5s/8s，让我复核是否把这类现象误判成 UI 问题。

**没有误判**：本次审计里没有记录过任何「点按钮没反应」的结论。
与操作按钮有关的唯一发现是 §3 —— 操作列在 390x844 下 `display:none`，
由探针量出 `getComputedStyle().width = 0`，属于「按钮根本不存在」，
不是「按钮存在但点了没响应」。两者现象与修法都不同（前者改 CSS，后者查数据流）。

缓存与刷新时机的修复对后续**功能验证**有价值（测启停时不会再被 8 秒 TTL 骗），
但不影响本次的布局结论。
